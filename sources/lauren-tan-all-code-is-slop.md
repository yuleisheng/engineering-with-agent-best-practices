# Source review: Lauren Tan, *All Code Is Slop (Except Mine)*

Lauren Tan (Grok Bot, SpaceXSI), AI Engineer CODE 2026, November 11, 2026. [Standalone video](https://www.youtube.com/watch?v=O_zcc6Xl12g), published November 14, 2026. Timestamps refer to the standalone video unless marked as livestream.

**Evidence reviewed:** AI Engineer's [timestamped full transcript and slide captures](https://ai.engineer/talks/O_zcc6Xl12g-all-code-is-slop-except-mine) and [livestream transcript](https://ai.engineer/api/code/reading-download/transcripts/lauren-tan.md?raw=1). The talk is a first-person account with concrete examples from Grok Bot and earlier work at Cursor. Its internal implementation and reported results remain single-source; external references below support particular techniques or counterexamples, not the team's private workflow or metrics.

The [precedent study](https://arxiv.org/html/2610.38244v1) supports effects on implementation choice in tested API tasks, not general code quality. Don't copy Dune's folder layout or clean up an entire repo for its own sake. [Practice](../practices/make-good-patterns-discoverable.md). |
| [5:00](https://www.youtube.com/watch?v=O_zcc6Xl12g&t=300s) introduces Dune, an internal Electron client framework. Profile a timing problem before assuming the same cause. Fix or constrain the specific misuse after providing a viable alternative. [Practice](../practices/enforce-repeatable-rules.md). |
| The [6:55 slide](https://www.youtube.com/watch?v=O_zcc6Xl12g&t=415s) targets unsolicited Markdown. The [8:18 slide](https://www.youtube.com/watch?v=O_zcc6Xl12g&t=498s) references pstack's `/no-comments` and charts a drop from 65,824 to 1,227 comments (98.1% net count decrease); Tan says “ban 99% of comments” at [8:23](https://www.youtube.com/watch?v=O_zcc6Xl12g&t=503s). | **Reject a comment-removal quota or blanket ban.** The slide shows a net count change, not a measured removal rate or quality gain. Keep concise rationale or constraints that code can't convey, as in [Google's code review guidance](https://google.github.io/eng-practices/review/reviewer/looking-for.html#comments). Enforce testable rules separately. |
| The [1:50 slide](https://www.youtube.com/watch?v=O_zcc6Xl12g&t=110s) shows issues feeding back into writing, and the [4:49 slide](https://www.youtube.com/watch?v=O_zcc6Xl12g&t=289s) makes a case for selective code reading. At [9:40–10:49](https://www.youtube.com/watch?v=O_zcc6Xl12g&t=580s), Tan describes running the app with feature maps and reusable drivers and reviewing verification artifacts. | **Keep runtime evidence; reject artifacts as a universal substitute for code review.** Review code for side effects, permissions, and failure paths artifacts cannot show. Triage, repair, and rerun the same acceptance check as a catalog recommendation, not a procedure quoted from the slide. [ExecCritic](https://arxiv.org/html/2609.09133v1) supports independently grounded, fixed checks for the repair tasks studied; weak checks can misdirect repair. [Practice](../practices/verify-real-behavior.md). |
| [10:50–11:50](https://www.youtube.com/watch?v=O_zcc6Xl12g&t=650s), [12:54–13:19](https://www.youtube.com/watch?v=O_zcc6Xl12g&t=774s): The team uses TLA+ for multi-device flows, Lean for parts of a virtualization algorithm, and Bombadil for property-based UI tests. Statecharts help reviewers see modeled intent. | **Keep targeted state and invariant checks; defer the tool choices to the repo.** Tan describes early successes, not a comparison with simpler tests. A model check or proof covers stated properties and assumptions; a runtime check covers behavior of the implementation. Keep the two separate. The pstack generators on the [10:36](https://www.youtube.com/watch?v=O_zcc6Xl12g&t=636s) and [10:56](https://www.youtube.com/watch?v=O_zcc6Xl12g&t=656s) slides are references, not established origins of the internal tools or models. [Practice](../practices/check-state-transitions.md). |
| At [12:05](https://www.youtube.com/watch?v=O_zcc6Xl12g&t=725s), Tan shows [Cindy Sridharan's post](https://x.com/copyconstruct/status/2118529738532925725) estimating that 70% of her daily tokens go to verifying patches. Tan says “most” of her own tokens go to verification at [12:13–12:20](https://www.youtube.com/watch?v=O_zcc6Xl12g&t=733s), and argues that agents make heavier verification cheaper at [12:22–12:50](https://www.youtube.com/watch?v=O_zcc6Xl12g&t=742s). | **Reject 70% as a budget target; defer the net cost claim.** Faster authoring does not establish lower total cost after review, flaky tests, and maintenance. |
| [Sridharan's testing-mix reply](https://x.com/copyconstruct/status/2118539184654938154), shown at [12:20](https://www.youtube.com/watch?v=O_zcc6Xl12g&t=740s), and the clearer [12:29 chart](https://www.youtube.com/watch?v=O_zcc6Xl12g&t=749s) show different checks in pre-production, deployment, release, and post-release. | **Keep with limits.** Match the check to the risk and stage. When local tests can't see a production-only risk, use an existing canary with representative traffic and a meaningful signal, or an existing post-release signal. [Google SRE's canary guidance](https://sre.google/workbook/canarying-releases/) supports this distinction. The chart isn't a mandatory checklist, evidence that Grok Bot uses every technique, or grounds for giving agents production access. [Practice](../practices/verify-real-behavior.md). |

At [13:39–13:44](https://www.youtube.com/watch?v=O_zcc6Xl12g&t=819s) Tan separately says about 11,000 PRs shipped to production. The talk doesn't isolate what caused the improvements. [Practice](../practices/measure-outcomes.md). |
