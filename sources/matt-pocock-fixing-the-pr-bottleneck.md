# Source review: Matt Pocock, *Fixing the PR Bottleneck*

Matt Pocock (AI Hero), [AI Engineer Paris 2026](https://ai.engineer/paris/2026), September 24, 2026. [Standalone video](https://www.youtube.com/watch?v=LlgiOCmFG_w), listed by YouTube as published September 25, 2026. Timestamps refer to that recording.

**Evidence reviewed:** AI Engineer's [full published transcript, slide captures, and embedded examples](https://ai.engineer/talks/LlgiOCmFG_w-fixing-pr-bottleneck): all 47 transcript segments and 17 available slide captures, plus the test, architecture report, and CLI sketch images. The publisher notes poor early audio and the opening transcript has a gap. No complete slide deck was available on the talk page. The examples show what a test asserts or what an artifact looks like; the talk gives no measured comparison of review quality, reviewer time, or net cost. The workflow results are single-source. Pocock's [subsequent v1.3.0 release](https://github.com/mattpocock/skills/releases/tag/v1.3.0) clarifies how the published skills work, not what the onstage versions did or whether the workflow pays off.

| [1:50–2:20](https://www.youtube.com/watch?v=LlgiOCmFG_w&t=110s): Incoming reports could trigger agent work; PlanetScale slow-query reports are a hypothetical example. | **Defer.** The talk doesn't establish when a signal merits an automated PR or how to keep the queue reviewable. Use a [bounded pilot](../practices/validate-before-scaling.md) before automating intake. | Signals don't reliably identify actionable work, or reviewers can't keep up with the resulting drafts. |
| [2:20–2:50](https://www.youtube.com/watch?v=LlgiOCmFG_w&t=140s): Existing code is the environment the agent works in, so bad patterns can propagate. | **Keep with limits.** This echoes [Tan's account of agents copying precedent](lauren-tan-all-code-is-slop.md). Point agents to a maintained example before cleaning up older ones; neither talk measures the effect of a broad cleanup. [Practice](../practices/make-good-patterns-discoverable.md). | The alternate pattern is still legitimate or isn't what caused the mistakes. |
| [2:50–3:36](https://www.youtube.com/watch?v=LlgiOCmFG_w&t=170s): Layer deterministic checks, automated review, and human review in that order. | **Keep with limits.** Checks catch repeatable failures before people spend attention, echoing [Tan's Poteto pyramid](lauren-tan-all-code-is-slop.md). The talks organize the layers differently but both put enforceable rules first. [Practice](../practices/enforce-repeatable-rules.md). | An extra automated reviewer duplicates existing work or costs more to triage than it saves. |
| [3:51–4:50](https://www.youtube.com/watch?v=LlgiOCmFG_w&t=231s): Deterministic checks are cheap enough to add liberally. | **Keep with limits.** Add a check for a known gap. Pocock allows for tokens spent on fixes; test authoring, flake triage, runtime, and maintenance also count. [Practice](../practices/enforce-repeatable-rules.md). | The check is unreliable, duplicates existing coverage, or costs more than the failure it prevents. |
| [5:55](https://www.youtube.com/watch?v=LlgiOCmFG_w&t=355s) shows a test asserting a post limit constant is 280. [6:34](https://www.youtube.com/watch?v=LlgiOCmFG_w&t=394s) shows a test checking section order in TypeScript source instead of the rendered page. [7:22–7:52](https://www.youtube.com/watch?v=LlgiOCmFG_w&t=442s) describes a stub for the browser's AudioContext that can't reproduce its real failures. | **Keep with limits.** Exercise the contract and show a plausible wrong implementation fails. The talk names no specific AudioContext error or measured frequency of weak tests. [Google's test-doubles guidance](https://abseil.io/resources/swe-book/html/ch13.html) corroborates the fidelity problem and explains when a stub can force a rare failure safely. [Practice](../practices/verify-real-behavior.md). | Source structure itself is the contract, or the real dependency is unsafe or impractical to exercise for this case. |
| [8:41–9:35](https://www.youtube.com/watch?v=LlgiOCmFG_w&t=521s): Ousterhout's deep modules hide substantial behavior behind a small interface that tests can use. At [9:52–10:52](https://www.youtube.com/watch?v=LlgiOCmFG_w&t=592s), Pocock shows a refactor proposal and describes his design vocabulary. | **Keep with limits.** Test through a supported interface first; improve one boundary only when reaching behavior through it is repeatedly hard. [Ousterhout's book excerpt](https://web.stanford.edu/~ouster/cgi-bin/aposd2ndEdExtract.pdf) explains information hiding. The report proposes consolidating three visibility checks; it doesn't show a shipped refactor or better tests. [Practice](../practices/verify-real-behavior.md). | The existing interface already works for tests, or the refactor would hide conditions callers need to know. |
| [11:30–12:21](https://www.youtube.com/watch?v=LlgiOCmFG_w&t=690s): Pocock says giving standards to the implementer makes it “perform worse,” without a measured comparison. [12:21–13:21](https://www.youtube.com/watch?v=LlgiOCmFG_w&t=741s): A separate reviewer gets the diff, repo standards, and its own context. At [13:51–14:22](https://www.youtube.com/watch?v=LlgiOCmFG_w&t=831s), he puts standards in the reviewer's file rather than the implementer's guidance. | **Keep with limits.** Unlike [Tan](lauren-tan-all-code-is-slop.md), who retains judgment prose in agent guidance, Pocock puts standards in the review context. The [context-file study](https://arxiv.org/html/2602.11988v3) found agents generally followed instructions and recommends context files for non-standard practices, despite higher inference costs and no general task-success gain in the tested settings. It didn't compare separate review contexts. Keep essential instructions up front; test the detailed second pass on known good and bad diffs. [Practice](../practices/review-against-repo-standards.md). | The reviewer-only rule is needed to implement the change safely, or the second pass doesn't catch enough to justify the handoff. |
| [14:22–15:21](https://www.youtube.com/watch?v=LlgiOCmFG_w&t=862s): Attendees mention Cursor Bugbot and CodeRabbit; Pocock advises against outsourcing automated review. | **Reject.** Choose by fit and permissions rather than who builds the reviewer. [Bugbot documents repo-specific rules](https://cursor.com/docs/bugbot#rules); that's a counterexample to assuming third-party tools can't be tuned, not proof of review quality. [Practice](../practices/review-against-repo-standards.md). | An existing reviewer can already apply the repo's standards and meet its access and data-handling requirements. |
| [15:22–16:12](https://www.youtube.com/watch?v=LlgiOCmFG_w&t=922s): Pocock prefers reviewer commits to comments, except when unsure. | **Keep with limits.** [Sun et al., Table IX](https://arxiv.org/html/2508.18771v2#S4.T9) classified 60% of human comments and 0.9–19.2% of AI comments across four tools as both valid and at least partly addressed. The discussion calls these rates among valid comments, but the table uses all comments by source. This supports the concern about low-yield comments, not a claim about reviewer time or the superiority of autofixes. The released `code-review` skill reports findings; [Bugbot offers opt-in Autofix](https://cursor.com/docs/bugbot#autofix) in `newBranch` or `existingBranch` mode. Keep the useful part: propose suggestion blocks or separate-branch patches for the author to verify and apply, with no pushes to the PR branch or merge rights. [Practice](../practices/review-against-repo-standards.md). | The fix is uncertain, more work to verify than to write, or requires giving the reviewer access to change or merge the PR. |
| [17:44–18:43](https://www.youtube.com/watch?v=LlgiOCmFG_w&t=1064s): Describe “merge danger” with reversibility and blast radius; reverting code cannot unsend email. [18:44–19:43](https://www.youtube.com/watch?v=LlgiOCmFG_w&t=1124s): Use a compact sketch, borrowing from HumanLayer's Show Me skill, when it clarifies the change. | **Keep with limits.** Specify what rollback restores and who could be affected. [Amazon's rollback guidance](https://builder.aws.com/content/3F04j2yRAAMBuPSPs50xwXZqg01/ensuring-rollback-safety-during-deployments) corroborates testing compatibility with data already written. A CLI sketch can show a new command and flags, but can't show they ran. [Practice](../practices/show-merge-risk.md). | A risk label would be accepted without checking recovery or scope, or a diagram would obscure the change rather than clarify it. |
| [21:44–22:20](https://www.youtube.com/watch?v=LlgiOCmFG_w&t=1304s): Review every one-way door, but not necessarily every two-way door. | **Reject.** Don't waive required review based on the label. [Amazon's automated deployment example](https://builder.aws.com/content/3ErTKQOTKc5NIw031UePBPxTQ6I/automating-safe-hands-off-deployments) keeps human review before merge. Put more attention on wide, irreversible, or uncertain changes. [Practice](../practices/show-merge-risk.md). | The change can affect many users before rollback, leaves side effects, or has to satisfy an approval policy. |
| [20:14–21:54](https://www.youtube.com/watch?v=LlgiOCmFG_w&t=1214s): Pocock describes Retro taking a session, a PR plus session, or a batch of PRs and reviews to suggest workflow improvements. | **Keep with limits.** The [v1.3.0 Retro skill](https://github.com/mattpocock/skills/blob/v1.3.0/skills/engineering/retro/SKILL.md) reads session material; PR reviews as a standalone input come from the talk. Its split between checks for mechanical violations and `CODING_STANDARDS.md` for judgment matches the [repeatable rules practice](../practices/enforce-repeatable-rules.md). [Google's SRE Workbook](https://sre.google/workbook/postmortem-culture/) supports concrete, verifiable prevention work after incidents, not Retro's effect on PR time or tokens. Start with diffs and comments; avoid raw session logs. | The correction is a one-off, there's no way to tell if the fix prevents recurrence, or reviewing raw sessions would expose sensitive material. |
