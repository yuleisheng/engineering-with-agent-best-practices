# Source review: Matt Pocock, *Fixing the PR Bottleneck*

Matt Pocock (AI Hero), [AI Engineer Paris 2026](https://ai.engineer/paris/2026), September 24, 2026. [Standalone video](https://www.youtube.com/watch?v=LlgiOCmFG_w), listed by YouTube as published September 25, 2026. Timestamps refer to that recording.

**Evidence reviewed:** AI Engineer's [full published transcript, slide captures, and embedded examples](https://ai.engineer/talks/LlgiOCmFG_w-fixing-pr-bottleneck): all 47 transcript segments and 17 available slide captures, plus the test, architecture report, and CLI sketch images. The publisher notes poor early audio and the opening transcript has a gap. No complete slide deck was available on the talk page. The examples show what a test asserts or what an artifact looks like; the talk gives no measured comparison of review quality, reviewer time, or net cost. The workflow results are single-source. Pocock's [subsequent v1.3.0 release](https://github.com/mattpocock/skills/releases/tag/v1.3.0) clarifies how the published skills work, not what the onstage versions did or whether the workflow pays off.

## Claim decisions

| Source claim or example | Verdict and reason |
| --- | --- |
| [1:50–2:20](https://www.youtube.com/watch?v=LlgiOCmFG_w&t=110s): Incoming reports could trigger agent work; PlanetScale slow-query reports are a hypothetical example. [2:50–3:36](https://www.youtube.com/watch?v=LlgiOCmFG_w&t=170s): Use deterministic checks, automated review, and human review as three layers. | **Keep the order; defer automatic intake.** Checks catch repeatable failures before people spend attention. The talk doesn't establish when a signal merits an automated PR or how to keep that queue reviewable. Keep the existing [bounded pilot](../practices/validate-before-scaling.md); no new intake or merge permissions follow from this example. |
| [4:21–4:50](https://www.youtube.com/watch?v=LlgiOCmFG_w&t=261s): Deterministic checks are cheap enough to add liberally. | **Keep targeted checks; reject “just CPU cycles” as a cost model.** Pocock allows for tokens spent on fixes. Test authoring, flake triage, runtime, and maintenance also count. Start with one check that fixes a known gap. [Practice](../practices/enforce-repeatable-rules.md). |
| [5:55](https://www.youtube.com/watch?v=LlgiOCmFG_w&t=355s) shows a test asserting a post limit constant is 280. [6:34](https://www.youtube.com/watch?v=LlgiOCmFG_w&t=394s) shows a test checking section order in TypeScript source instead of the rendered page. [7:22–7:52](https://www.youtube.com/watch?v=LlgiOCmFG_w&t=442s) describes a stub for the browser's AudioContext that can't reproduce its real failures. | **Keep behavior checks; reject a blanket ban on doubles.** Exercise the contract and show a plausible wrong implementation fails. The talk names no specific AudioContext error or measured frequency of weak tests. [Google's test-doubles guidance](https://abseil.io/resources/swe-book/html/ch13.html) corroborates the fidelity problem and explains when a stub is useful to force a rare failure safely. A source check is appropriate if source structure itself is the contract, not if the claim is that the UI looks right. [Practice](../practices/verify-real-behavior.md). |
| [8:41–9:35](https://www.youtube.com/watch?v=LlgiOCmFG_w&t=521s): Ousterhout's deep modules hide substantial behavior behind a small interface that tests can use. At [9:52–10:52](https://www.youtube.com/watch?v=LlgiOCmFG_w&t=592s), Pocock shows a refactor proposal and describes his design vocabulary. | **Keep with limits.** Test through a supported interface first; improve one boundary only when reaching behavior through it is repeatedly hard. [Ousterhout's book excerpt](https://web.stanford.edu/~ouster/cgi-bin/aposd2ndEdExtract.pdf) explains information hiding and warns against obscuring details callers need. The example report proposes consolidating three visibility checks; it doesn't show a refactor was implemented or produced better tests. [Practice](../practices/verify-real-behavior.md). |
| [12:21–13:21](https://www.youtube.com/watch?v=LlgiOCmFG_w&t=741s): A separate reviewer gets the diff, repo standards, and its own context. At [13:51–14:22](https://www.youtube.com/watch?v=LlgiOCmFG_w&t=831s), Pocock recommends not giving coding standards to the implementer through `agents.md`. | **Keep a focused second pass; reject hiding essential instructions.** Give implementers intent, safety constraints, and required checks up front. Give reviewers the detailed rubric and surrounding code. The [context-file study](https://arxiv.org/html/2602.11988v3) found higher inference cost without a general task-success gain from context files in its settings; it didn't compare separate review contexts. Test the review pass against known good and bad diffs before relying on it. [Practice](../practices/review-against-repo-standards.md). |
| [14:52–15:21](https://www.youtube.com/watch?v=LlgiOCmFG_w&t=892s): Don't outsource automated review. At [15:53–16:12](https://www.youtube.com/watch?v=LlgiOCmFG_w&t=953s), Pocock says commits, not comments, should be the reviewer's default. | **Reject both as defaults.** Repo fit matters more than who hosts the reviewer: he mentions attendees using Cursor Bugbot and CodeRabbit; [Bugbot documents repo-specific rules](https://cursor.com/docs/bugbot#rules). A [GitHub Actions study](https://arxiv.org/html/2508.18771v2) found some concise, concrete comments were more likely to lead to edits; that isn't proof of quality or a comparison against autofixes. The published `code-review` skill reports findings, not commits. Start read-only; make review findings easy to confirm and don't give a reviewer write or merge access just to reduce comments. [Practice](../practices/review-against-repo-standards.md). |
| [17:44–18:43](https://www.youtube.com/watch?v=LlgiOCmFG_w&t=1064s): Describe “merge danger” with reversibility and blast radius; reverting code cannot unsend email. [18:44–19:43](https://www.youtube.com/watch?v=LlgiOCmFG_w&t=1124s): Use a compact sketch, borrowing from HumanLayer's Show Me skill, when it clarifies the change. | **Keep with limits.** Specify what rollback restores and who could be affected. [Amazon's rollback guidance](https://aws.amazon.com/builders-library/ensuring-rollback-safety-during-deployments/) corroborates the need to test compatibility with data already written. The CLI sketch shows a new command and two flags, not executed evidence. Use the smallest useful explanation; a diagram isn't a requirement. [Practice](../practices/show-merge-risk.md). |
| [21:44–22:20](https://www.youtube.com/watch?v=LlgiOCmFG_w&t=1304s): Review every one-way door, but not necessarily every two-way door. | **Reject skipping required review based on the label.** An easy recovery can still leave a broad impact. [Amazon's automated deployment example](https://aws.amazon.com/builders-library/automating-safe-hands-off-deployments/) keeps human review before merge. Put more attention on wide, irreversible, or uncertain changes without loosening gates. [Practice](../practices/show-merge-risk.md). |
| [20:14–21:54](https://www.youtube.com/watch?v=LlgiOCmFG_w&t=1214s): Retro uses an agent session, a PR plus session, or a batch of PRs and reviews to suggest changes to checks, standards, navigation, tool use, or bloated instructions. | **Keep a small feedback loop, not a new ceremony.** Pick a recurring, material correction; fix the actual gap and check that the next relevant change behaves differently. [Google's SRE Workbook](https://sre.google/workbook/postmortem-culture/) likewise argues for concrete, verifiable prevention actions after incidents. That's not evidence for Retro's effect on PR time or token use. Start with diffs and comments; don't share raw session logs. [Practice](../practices/enforce-repeatable-rules.md). |
